# EduBench · 教育场景大模型评测中台

按桌面 PRD 实现的本地 Demo。三个被测模型为豆包 Seed 2.1 Lite、DeepSeek V4.1 Flash、GLM-5.3-Flash（用户授权替换）；Judge 为 Qwen3.8-Max。没有生产演示假数据、假评分或随机模型结果。

## 功能与技术栈

- 管理端：Benchmark 维护、模型配置、真实调用与 Qwen 机评、评测人员管理、任务分配、进度和结果分析。
- 评测端：使用已分配姓名进入分配给自己的任务，对每题三个匿名回答按三个人工维度评分，支持草稿、提交与刷新恢复。
- 前端：原生 HTML、CSS、JavaScript，无框架与打包依赖。
- 后端：Node.js 内置 HTTP 服务、`fetch` 与 `node:sqlite`，SQLite WAL 持久化。
- 模型接口：豆包原生 Responses；DeepSeek、GLM 和 Qwen 使用兼容 Chat Completions 协议。
- 测试：Node.js 内置测试运行器，使用隔离临时数据库和本地协议夹具。

源码无需编译或打包，也无需 `npm install`。GitHub Pages 仅用于总仓库的静态作品集，不能运行本项目的 Node.js 后端；本项目可按下文在本地启动或部署到 Railway。

## 启动

需要 Node.js 22.13 或以上（已在本机 Node 26 验证），无需安装任何 npm 依赖。

从总仓库根目录进入项目：

```sh
cd "飞象评测平台"
npm start
```

可选配置：仅在不存在 `.env` 时复制 `.env.example` 并填写 API 设置，保留现有配置。

也可双击项目内的 `启动 EduBench.command`。

- 统一入口：http://localhost:3000/，先选择「管理端」或「评测端」。
- 管理端：http://localhost:3000/admin
- 评测端：http://localhost:3000/review
- 停止服务：在启动终端按 Ctrl+C。

首次启动自动加载 `server/benchmark.json` 中从 PRD 原文提取的九条 Query、学科、学段、场景、Query 类型、背景和完整任务要求。无需重复上传。PRD 备份为 `PRD.md`，重新提取脚本为 `scripts/seed-from-prd.py`。

## 使用流程

1. 点击「创建评测任务」，进入连续四步配置页：**创建任务 → 配置 Benchmark → 分配人员 → 发布**。
2. 「创建任务」填写名称和说明，保存为草稿。草稿保存到 SQLite，可从任务列表「继续配置」恢复；此时不会调用模型，评测人员不可见。
3. 「配置 Benchmark」选择已预置九题或上传 JSON / CSV，可勾选本次参与题目并核对任务背景和完整要求。已有任务库和历史结果不会被覆盖。
4. 「分配人员」直接添加姓名，为每人勾选负责的 Query；公网模式可在本步骤生成个人评测码（只显示一次，请保存）。同一题可分配多人，每条题目至少有一位负责人员。
5. 「发布」先核对题目、人员和回答数。系统检查是否遗漏分配、个人评测码及模型 API 配置。模型页填写真实 Base URL、model ID 和 API Key；地址不要追加 `/chat/completions` 或 `/responses`。配置完成后可回到草稿继续发布。五维规则和权重在「评分规则」维护。
6. 点击「发布任务并启动真实评测」后，才开放评审访问并启动三个模型及 Qwen 独立机评；重复点击不会重复执行。题目、发布时的模型参数和评分规则形成快照。九题首轮正常共 72 次真实请求：27 次模型生成、9 次标准草案、9 次核对、27 次 Judge 评分；失败不会自动重试。
7. 详情页查看调用、Judge 与人工进度，复制评测链接分别发送给对应人员。评审输入姓名及公网个人评测码后，只看到自己获分配的已发布任务，每题三个匿名回答，分别按三个人工维度评 1—3 分。
8. 管理员查看每人的完成题数、未完成任务、提交时间和分数；已发布任务仍可调整人员范围。历史评分保留，移出范围的评分不计入当前汇总。Qwen 机评不依赖人工评分进度。
9. 「结果分析」按学科、模型、维度比较机评、人评及综合分，支持原始 JSON 与打印报告。Q08、Q09 原有失败回答继续保留失败，缺失分数留空，不补零。数据齐全后才显示最终排名。

升级兼容：历史批次保持已发布状态，已有输出、评分、匿名编码、个人评测码和人员范围不变。新增 `run_workflows` 表记录新任务的草稿步骤及发布时间；部署升级不覆盖数据库。

## 评分和数据一致性

- 自动机评：需求满足度 20%、输出完整性与规范性 20%。
- 人工盲评：知识真实性与准确性 25%、教学合理性与适配性 20%、教学实用性与创新性 15%。
- 每个 Query 先对同一模型的多位人工评审取均值，再对各 Query 等权平均，按 `Σ(维度平均分 × 百分比权重) ÷ 3` 得到 100 分制总分。
- 未评分不算 0。所有 Query 的机评与各题对应评测人员的人工评分均完成后，才给出模型最终综合得分和排名。每题必须至少分配一人；新人员被分配某题后，要等其完成该题才恢复最终结果。并列得分并列排名。
- 同一姓名恢复同一评审进度；重复提交更新原记录，不重复累计。不同评审的内容与分数互不展示。
- 原始正文不修改，匿名评测接口只返回随机编码与去掉品牌标识的正文，不返回模型 ID、厂商、响应时间、Token 或机评分数。
- Judge 先生成逐题标准，再发起独立核对请求，冻结后统一评价同题三个输出。草案、核对记录、分数和问题可在每个 Case 的详情追溯。
- JSON、维度分数及 1—3 分范围严格校验；无效 Judge 输出保留原响应并标记错误。输出被 Token 上限截断时保存部分内容，但不作为成功输出进入评分。
- SQLite 使用事务、外键与 WAL，数据库位于 `data/edubench.sqlite`。页面刷新、服务重启后数据保留。输入中的未提交评分草稿保存在当前浏览器，提交后写入服务端数据库。
- 服务重启会把正在发送的请求标记为中断，不自动重发，避免重复费用。管理员可重试；已成功生成、已冻结标准和成功机评会被跳过。失败请求可能已在供应商侧计费。

## 局域网多人评审

服务默认监听 `0.0.0.0:3000`，评审可使用 `http://这台电脑的局域网IP:3000/review?run=共享链接中的批次Token`。保持电脑和服务运行，并确保参与者能连通该端口。管理 API 仅允许本机回环地址访问，远程只能使用评测端。Demo 采用姓名入口，只允许管理员已分配的人员访问对应任务；姓名不是密码，适合受信任的小范围协作，未实现复杂账号体系。

## PRD 歧义处理

Q08 汇总表写“初中语文”，详细任务为高中《登泰山记》，采用详细任务的高中语文。末尾范围表写“五维自动评分”、人工模块写“五维人工评分”，与正文“两维机评＋三维人评”冲突，以正文和评分权重为准。用户更新后采用豆包 / DeepSeek / GLM 被测、Qwen Judge。

包含权重与缺失分数、多人 Query 等权、CSV 多行解析、Judge 格式校验、截断处理、九题三回答分发、人员新增与改名、未分配姓名拒绝、跨批次访问拒绝、取消与恢复分配、Qwen 独立机评、失败重试不重复调用、匿名接口、两人评分、修改不重复累计、服务重启后的评分与随机顺序恢复、任务删除关联清理。集成测试只使用独立临时数据库和显式测试协议夹具，不调用付费 API，也不会把测试数据写入实际 Demo。

真实接口诊断脚本（会发送实际 API 请求）：

```sh
node --env-file=.env scripts/check-models.js
node --env-file=.env scripts/verify-connections.js
```

诊断脚本只保存连通性信息，不会创建评测结果。日常使用可直接在管理页测试连接。

默认统一输出预算为 16,384 Token、超时 300 秒。GLM-5.3 强制思考，思考与正文均占用供应商输出预算；首次较低预算的截断记录保留于独立诊断批次。官方说明：https://docs.bigmodel.cn/cn/guide/capabilities/thinking-mode

GLM-5.3 在实际教学任务中出现超时与空正文，按用户明确选择改用 GLM-5.3-Flash。新批次通过 `snapshot.reusedFrom` 记录来源，复用相同参数下的豆包、DeepSeek 真实输出与冻结标准，GLM 全部重新调用。原批次保留供追溯。

人员管理版本首次启动会自动迁移原有评审为人员档案，保留原评审 ID、访问会话、匿名编码和评分。新人员须由管理员添加与分配。所有时间以北京时间显示，数据内保存 ISO 时间。

按 Query 分配版本首次启动会为已有人员迁移其原有的整批任务范围，保留匿名编码与评分。管理员可在「分配人员」分别选择每人负责的 Query，评测端、提交权限及进度统计均以当前范围为准；机评独立执行。

失败步骤重试接口可选传入 `timeoutMs`（10000—600000），仅调整本次未成功请求的等待上限，不改写批次快照或生成参数。实际成功调用的等待上限记录在 `usage.request.timeoutMs` / Judge 调用元数据中；已成功的生成、冻结标准和机评仍跳过。

截断后的失败生成请求可选传 `maxTokens`（256—65536），只影响本次尚未成功的生成步骤；Judge 预算及已成功步骤保持原样。实际参数在输出详情「查看实际生成调用参数」中可查，原始批次快照保留用于追溯。对比结果时应考虑重试时预算差异。

## 公网部署（Railway）

使用单个 Node.js 服务和持久卷，不需要额外数据库服务。仓库根目录设置为 `飞象评测平台`；使用项目 Dockerfile（Node.js 24），启动 `node server/index.js`。持久卷挂载 `/data`，运行变量 `NODE_ENV=production`、`DATA_DIR=/data`、`ADMIN_PASSWORD_HASH`（scrypt 哈希，非明文密码）。可配置 `PUBLIC_ORIGIN=https://实际域名` 强制同源校验。

公网模式不再信任本机 IP 判断管理员权限：管理员必须登录，12 小时会话保存在共享数据库，Cookie 为 HttpOnly、Secure、SameSite=Strict。评测人员输入姓名及独立评测码；评测码只存 scrypt 哈希。管理员可在人员管理生成或重置评测码，旧会话随之失效，评分与任务范围保留。登录接口限制连续尝试次数。

运行 `node scripts/prepare-cloud.js` 创建私有迁移目录：一致性复制现有数据库，清除模型 API Key 与管理员会话，并为云端生成独立管理员密码及人员评测码。它不会改动源库，不调用模型。目录在 `data/` 内，被 Git 和 Docker 排除；密码与评测码只保存在该目录的 `credentials.json`，平台仅填写 `deployment.env` 中的哈希。数据库通过平台私有 CLI/卷传输，不提交 GitHub，不放入镜像。导入应在服务停止时进行，只允许空目标库；上线后不再覆盖共享库。

本轮仅评已有回答，云端可以不提供任何模型密钥。以后要生成新批次时，再在服务端配置模型 API，密钥不得进入前端或仓库。部署后需配置持久卷备份，并保留评测结束时的下载备份。单实例即可支持三人同时使用，禁止将 SQLite 复制到多个副本独立写入。

Q08、Q09 的 GLM 失败回答继续显示失败，报告和结果分析明确列出原因，对应评分与综合分以「—」显示，不补零、不生成假评分；维度均分仅反映当前有效数据，缺失数据的模型总分和最终完整排名继续留空。上线不会自动重试任何失败模型请求。
