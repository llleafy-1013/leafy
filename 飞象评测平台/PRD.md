# 一、项目背景与产品定位

## 项目背景

随着大语言模型在教育领域的应用不断深入，AI 已经逐渐参与到教学设计、知识讲解、习题生成、实验方案设计、课件制作、学习辅导等多个环节。

但不同模型在教育场景中的表现存在差异。通用模型虽然具备较强的文本生成和知识理解能力，但在实际教学应用中，仍可能出现以下问题：

- **知识准确性不足：** 存在学科知识错误、概念混淆、公式错误或对文本材料的过度解读。

- **教学适配性不足：** 生成内容与课程标准、教材要求、学段特征或学生认知水平不匹配。

- **教学逻辑不合理：** 教学环节衔接不畅、课堂时间分配不合理、教学主线不清晰。

- **资源实用性不足：** 生成内容看似完整，但缺乏可操作性，教师仍需进行大量修改。

- **专业场景能力不足：** 在实验设计、专业实践、复杂知识推理等场景中，可能出现不准确或不符合实际条件的内容。

目前，教育大模型的评价不能仅依靠通用语言能力指标，也不能仅通过单次主观体验判断模型质量。需要建立面向教育业务场景的标准化评测体系，对不同模型进行统一测试、客观比较和问题诊断。

因此，本项目计划构建 EduBench 教育大模型综合能力评测平台，通过 Benchmark 管理、Evaluation Harness、多模型统一调用、自动化评分、人工盲评和评测报告等能力，形成标准化、可复用的教育大模型评测流程。

## 产品定位

EduBench 是一个面向教育场景的 AI 大模型综合能力评测平台。

平台通过构建多学科、多学段、多任务的标准化 Benchmark，对接不同模型服务，自动执行评测任务，结合规则评分、模型辅助评分和人工盲评，对模型在教育场景中的表现进行量化评价与问题分析。

**产品核心价值：**

1. **统一评测：** 统一管理不同厂商模型和测试任务，降低模型横向比较成本。

2. **标准化测试：** 建立教育场景 Benchmark，保证测试输入、评价维度和评分规则相对一致。

3. **自动化执行：** 通过 Evaluation Harness 自动完成模型调用、结果收集、评分和数据汇总。

4. **多维度评价：** 结合自动机评与人工盲评，降低单一评分方式带来的偏差。

5. **辅助决策：** 通过评测报告识别模型优势与不足，为模型选型、优化和教育产品应用提供依据。

### 反馈归纳

**教师对教育 AI 的核心需求：从内容生成工具转向真正理解教学需求的智能助教**

目前教师使用 AI 的主要目的，是辅助完成教案设计、教学内容补充和 PPT 课件制作，降低备课过程中的信息检索、内容组织和视觉设计成本。教师通常已经具备基本的教学思路，希望 AI 在此基础上进一步完善教学设计，而不只是机械地执行指令。

从实际使用反馈来看，教育 AI 已经展现出一定价值：能够理解自然语言需求、生成教学内容、整合优秀教学案例，并在课件视觉设计和互动工具生成方面提高备课效率。其中，主动检索教学资源、结合参考案例进行内容生成，是让教师感到惊喜的能力。

但现阶段仍存在一些突出问题：

1. **专业性不足：** 对国家课程标准、教材内容和学科知识的理解与落实不够充分，部分学科还可能出现知识解读偏差，甚至盲目接受用户提供的错误前提。

2. **教学设计不够合理：** 教学环节之间的逻辑衔接、课堂时间分配和教学主线把握仍有不足，容易出现环节过多、内容零散或不符合实际课堂节奏的问题。

3. **教学适配性不足：** 对不同学段、学生认知水平和实际学情的考虑不够充分，生成内容可能存在难度不匹配、教师难以直接应用等情况。

4. **实际使用体验有待完善：** 教学素材的丰富性、课件下载与编辑能力、视觉风格适配，以及对教师个人偏好和教学要求的持续记忆等方面仍有改进空间。

**综合来看，教师真正需要的并不是一个单纯能够生成教案和 PPT 的 AI 工具，而是一个具备专业教学理解能力、能够主动发现问题并辅助完善教学设计的智能助手。**

因此，教育大模型的评测不能仅关注内容生成是否流畅、课件是否美观，还应重点考察以下能力：

- **需求理解与指令执行：** 能否准确理解教师意图并落实具体要求。

- **知识准确性与课程标准适配：** 能否正确理解学科知识、教材和国家课程标准。

- **教学设计合理性：** 能否保证教学目标、内容、活动和时间安排之间的逻辑一致。

- **主动辅助与内容补充：** 能否发现教师未明确提出但实际需要的内容缺口，并提供有效补充。

- **实际教学可用性：** 生成结果能否适应真实课堂，减少教师后续修改成本。

- **交互与视觉呈现质量：** 课件是否美观、清晰，交互设计是否实用。

**对 EduBench 的启发：** 我们的评测重点应该从「模型能不能生成教育内容」转向**「模型生成的内容能不能真正帮助教师完成教学工作」**。尤其要把课程标准与教材适配、教学逻辑、主动补充能力作为重点评测方向。

需要说明的是，目前这些结论来自少量教师的探索性访谈，适合用于提出评测假设和设计首期 Benchmark，后续还需要更多教师试评来验证。

# 二、应用场景

## A\. 基础教育

**适用对象：** 小学、初中、高中教师及教研人员。

主要应用场景：

- 教学设计：教案生成、教学目标设计、教学流程规划。

- 教学内容开发：知识讲解、情境导入、习题生成。

- 教学资源开发：课件结构、教学素材、视频脚本。

- 实验教学：实验方案、操作指导、实验反思。

- 学习辅助：错题分析、知识点讲解、分层练习。

首期 Demo 的主要验证范围。

## B\. 高等教育

**适用对象：** 普通本科院校、高校专业课教师及科研教学人员。

主要应用场景：

- 专业课程教学设计与教学资料生成。

- 专业知识讲解、案例分析与课程拓展。

- 学术文献辅助阅读与知识整理。

- 实验教学方案与课程实践任务设计。

- 课程作业、考核题目及评价标准生成。

该类场景涉及专业知识深度和学术规范要求，纳入平台长期应用范围，首期暂不开展深入专业评测。

## C\. 职业教育与专科教育

**适用对象：** 高职院校、职业技术学院、专科院校教师及实训指导人员。

主要应用场景：

- 职业技能课程教学设计。

- 岗位任务与工作情境设计。

- 实训项目、操作流程及实训指导书生成。

- 职业技能考核题目与评分标准设计。

- 产教融合案例及行业应用资源开发。

重点关注模型生成内容的岗位适配性、实践可操作性和职业规范符合程度。

## D\. 其他教育场景

**适用对象：** 成人教育、继续教育、职业培训、校外教育机构及教育内容服务机构。

主要应用场景：

- 培训课程设计。

- 教学材料与知识讲义生成。

- 课程练习与能力测评。

- 个性化学习资源开发。

- 教学内容的多形式转换与整理。

上述场景作为产品未来的扩展方向，不作为首期 Demo 的实际验证任务。

# 三、评测体系设计

## 评测对象

### 首期评测对象

平台首期选取国内三家具有代表性的通用大模型厂商作为评测对象，三家厂商均提供面向开发者的模型 API，能够支持平台进行统一接入与自动化调用。考虑到 Demo 阶段的开发周期及 API 调用成本，优先选择各厂商当前可用的轻量级、低成本模型版本，在满足基础任务执行能力的前提下，控制评测成本。

### 模型接入与评测原则

为保证不同模型之间的评测具有可比性，平台采用统一的模型接入与调用规范：

1. **统一接入：** 通过各厂商官方 API 接入模型，使用统一的 Model Adapter 封装不同厂商的接口差异，实现模型配置、调用及结果采集的标准化。

2. **统一测试：** 使用相同的 Benchmark 数据集，将同一组 Query 分别提交给不同模型，保证测试任务和输入条件一致。

3. **统一参数：** 尽可能统一温度、输出长度等调用参数；对于不同模型不支持的参数，记录实际配置，避免将接口差异误认为模型能力差异。

4. **统一评估：** 使用相同的评测维度与评分规则，对模型输出进行自动化评分和人工盲评。

### Judge 模型选择

**选用模型：Qwen3\.8\-Max**

**模型ID：qwen3\.8\-max**

**模型定位：** 

作为独立评测模型（LLM Judge），负责对被测模型的输出进行自动化评分，不参与被测模型的横向排名。

**评测职责：**

Judge 仅负责以下两个机评维度：

- 需求满足度（权重 20%）

- 输出完整性与规范性（权重 20%）

**配置说明：**

Demo 阶段统一使用**Qwen3\.8\-Max**作为 Judge 模型，三个被测模型共用同一评测标准，避免因评分标准不一致影响横向对比。Judge 在每条 Query 上生成并核对评分标准后，将该标准固定，并统一应用于三个被测模型的输出，避免因评价标准变化影响横向比较。

## 评测任务

平台采用「学科 × 教育阶段 × 任务类型」的组织方式，对不同教育场景下的大模型能力进行分类评测。首期以基础教育阶段的教学辅助任务为主，优先选择教师高频使用、生成结果便于人工判断的任务类型，控制 Demo 的数据构建和测试成本。

### 评测任务分类

#### 一级：教育任务类型

首期聚焦以下三类核心任务：教学设计、讲解与习题、课件与教学资源。

以上三类任务覆盖教师日常备课中的主要 AI 使用场景。其中，课件与教学资源设计作为首期重点测试方向。

实验资源开发、情境拓展资源等暂不单独设置任务类别，可在后续版本中根据实际需求扩展。

#### 二级：学科与教育阶段

首期评测重点面向基础教育阶段，选择以下三个学科：小学数学、中学语文、中学历史。

选择不同学科和学段，主要用于观察模型在不同知识类型、教学要求及学生认知水平下的表现。

高校专业课程、职业教育与专科教育等作为后续扩展方向，首期不进行深入测试。

#### 三级：Query 类型

首期 Query 按照教师输入信息的明确程度及任务约束复杂度，分为以下三种类型：

首期 Benchmark 将覆盖以上三种 Query 类型，通过不同信息完整度和约束复杂度的输入，观察模型在开放需求理解、明确任务执行及复杂要求处理方面的表现。

其中：

- 开放模糊型重点观察模型是否能够主动理解和补全需求，而非机械生成内容。

- 明确任务型重点观察模型能否准确理解输入材料，并完成指定任务。

- 多约束任务型重点观察模型能否同时满足多项要求，避免遗漏、冲突或执行偏差。

三类 Query 均采用可直接验证的教学任务，首期不单独设置错误知识前提、争议知识等问题挑战测试，以控制人工核验成本。

### 首期 Query

首期计划对应评测任务的类型，构建9条标准化 Query。

每条 Query 配置：

- 任务名称及分类信息；

- 学科与教育阶段；

- 标准化输入内容；

- 通用评测维度及评分标准；

- 任务要求及相关背景信息。

通过三家模型对同一批 Query 进行测试，收集模型输出，开展自动化评分和人工盲评，形成模型横向对比结果。

#### 教学设计

##### Q01｜开放模糊型：小学数学单元教学设计

**学科：** 小学数学
**教育阶段：** 小学四年级
**任务场景：** 初步教案设计
**Query 类型：** 开放模糊型

## 评测方式

EduBench 采用「自动化机评 \+ 人工评审」相结合的方式，对模型在教育教学场景中的综合能力进行评估。

- **机评（自动化评测）：** 主要检查模型是否理解并完成教师提出的任务要求，包括需求覆盖、格式规范、明确约束、时间分配、必要内容完整性等可验证项目。

- **人评（人工评审）：** 主要评价模型输出的真实性、专业性、教学合理性和实际应用价值，包括知识准确性、学段适配、教学逻辑、资源质量和创新性等需要结合具体教学情境判断的内容。

## 评测维度

### 机评维度（2项）

|**机评维度**|**1分（较差）**|**2分（合格）**|**3分（优秀）**|
|---|---|---|---|
|**需求满足度**|未完成多项明确要求，存在明显遗漏或偏离任务。|完成大部分要求，但仍有部分要求遗漏或执行不充分。|完整响应各项明确要求，没有明显遗漏或偏离。|
|**输出完整性与规范性**|缺少多个必要模块，或明显违反格式、数量、时间等要求。|基本满足结构要求，但存在少量内容缺失或格式、数量等问题。|必要模块齐全，格式规范，数量及时间等约束均符合要求。|

### 人评维度（3项）

均采用1—3分制，由对应学科评审人员进行盲评。

|**人评维度**|**1分（较差）**|**2分（合格）**|**3分（优秀）**|
|---|---|---|---|
|**知识真实性与准确性**|存在明显错误、编造或不合理解读。|核心知识基本正确，但存在少量错误或表述不严谨。|知识准确、内容有依据，无明显错误或编造。|
|**教学合理性与适配性**|内容与教学目标不匹配，教学逻辑混乱或安排难以执行。|基本符合教学需求，整体流程合理，但部分内容仍需调整。|符合学生认知特点，教学目标明确，环节衔接自然且时间安排合理。|
|**教学实用性与创新性**|内容空泛或资源设计缺乏可操作性，难以直接用于教学。|具备基本实用性，但仍需教师进行一定修改，创新设计较为普通。|内容具体、资源易于使用，能有效促进学生参与，并提供有价值的教学启发。|

## 首期评分计算方式

### 评分权重：

|**类型**|**评测维度**|**权重**|
|---|---|---|
|机评|需求满足度|20%|
||输出完整性与规范性|20%|
|人评|知识真实性与准确性|25%|
||教学合理性与适配性|20%|
||教学实用性与创新性|15%|

### 加权计算公式：

综合得分 =（需求满足度得分 × 20% \+ 输出完整性与规范性得分 × 20% \+ 知识真实性与准确性得分 × 25% \+ 教学合理性与适配性得分 × 20% \+ 教学实用性与创新性得分 × 15%）÷ 3 × 100

### 整体得分计算： 

首先分别计算某一模型在 9 条 Query 中五个评测维度的平均得分，再按照各维度权重计算模型综合得分。对于同一 Query 存在多名人工评审的情况，先计算该 Query 对应维度的人工评分平均值，再参与后续汇总。

## 评测流程

### 评测流程概述

平台采用「评测准备—模型调用—结果采集—自动评测—人工评测—综合评分—报告生成」的评测流程，通过统一 Benchmark 和 Query，对多个大模型进行标准化测试，并结合 LLM 自动评测与人工盲评，形成最终评测结果。

整体流程如下：

01\. 评测准备
    ↓
02\. 模型调用
    ↓
03\. 结果采集
    ↓
04\. LLM 自动评测
    ↓
05\. 人工匿名盲评
    ↓
06\. 综合评分与数据分析
    ↓
07\. 生成评测报告

### **具体流程说明**

#### **阶段一：评测准备**

确定本次评测的测试范围及评测配置。

1. 上传或选择 Benchmark 测试集，包含标准化测试任务及对应 Query。

2. 选择参与评测的模型（豆包 Doubao Seed 2\.1 Lite、DeepSeek V4\.1 Flash、智谱 GLM\-5\.3）。

3. 配置 Judge 模型（Qwen3\.8\-Max**）**，用于后续自动评测。

4. 选择评价维度、维度权重及评分规则。

5. 创建评测任务，生成唯一任务 ID。

输出：评测任务及测试配置。

#### **阶段二：模型调用**

将 Benchmark 中的 Query 统一分发至各参测模型。

1. 系统读取测试集中的 Query。

2. 将相同 Query 分别发送至三个参测模型。

3. 采用并行调用方式执行模型请求。

4. 记录各模型的调用状态。

输出：各模型的生成请求及调用记录。

#### **阶段三：模型结果采集**

收集并保存各参测模型的生成结果及相关调用信息。

1. 获取模型返回的完整生成内容。

2. 保存模型名称、对应 Query、生成结果。

3. 记录响应时间、Token 消耗等数据。

4. 记录 API 调用失败、超时等异常信息。

输出：结构化模型生成结果。

#### **阶段四：LLM 自动评测**

1. 读取评测任务：Judge 获取当前 Query、任务背景、任务要求和两个评测维度。

2. 自主生成评分标准：根据具体任务要求和两个机评维度，生成当前 Query 对应的评分检查项及 1—3 分判断依据。

3. 检查评分标准：核对检查项是否覆盖任务核心要求，是否与两个评测维度对应，是否存在遗漏或重复。

4. 执行模型评测：使用核对后的评分标准，分别评价三个被测模型的输出，给出分数和评分理由。

5. 输出评测结果：保存评分标准、各模型得分、评分理由及问题记录，便于后续追溯。

输出：各模型的机评得分及分析结果。

#### **阶段五：人工匿名盲评**

邀请多名评测人员对模型生成结果进行独立评价。

1. 系统对模型输出进行匿名处理，隐藏模型名称及供应商信息，并采用随机编码和随机展示顺序，避免评审人员受到模型品牌和市场认知影响。

2. 生成评测页面和共享链接，评测人员通过共享链接进入评测页面。

3. 先输入评测人名字，根据三个评测维度给出的统一的评价标准，对每个维度分别进行评分。

4. 各评测人员独立提交评分，系统分别保存评分记录。

5. 所有评测人员完成后，系统汇总人工评分。

输出：各模型的人工评分及汇总结果。

#### **阶段六：综合评分与数据分析**

结合机评和人评结果，按照既定加权规则计算最终得分。

1. 汇总各模型的机评和人评得分。

2. 按照五个评价维度的权重计算维度得分。

3. 按照机评与人评的合成规则计算最终综合得分。

4. 对比不同模型在各维度、不同场景及 Query 类型下的表现。

5. 提取模型优势、短板及典型问题。

输出：各模型人评机评具体分数表格、所有模型综合得分排名表格、各维度排名及分析结果。

#### **阶段七：生成评测报告**

系统根据综合评分及数据分析结果，自动生成评测报告。

1. 展示各模型综合得分及排名。

2. 展示五个评价维度的评分表。

3. 展示不同模型的横向对比结果。

4. 生成模型表现的简要分析。

5. 展示典型优秀案例、失败案例及争议案例。

输出：完整的pdf模型评测报告。

## Evaluation Harness 设计

### **设计目标**

Evaluation Harness 是平台的核心执行模块，负责将 Benchmark 测试任务分发至不同模型，收集模型生成结果，并调用 Judge 模型完成自动评测。

首期重点实现多模型统一调用、结果采集、自动评分三个核心能力，保证一次评测任务能够完整执行并输出结构化评测数据。

### **核心执行流程**

上传 Benchmark（9条 Query）

↓

选择参测模型（豆包 Doubao Seed 2\.1 Lite、DeepSeek V4\.1 Flash、智谱 GLM\-5\.3）

↓

统一任务分发

↓

三个模型分别生成结果

↓

采集并保存27条生成结果

↓

调用 Judge 模型进行自动评分

↓

保存机评结果

↓

生成匿名人工评测任务

↓

多人独立完成人工评分

↓

汇总人工评分结果

↓

综合评分计算（机评 \+ 人评）

↓

生成最终评测结果

↓

进入结果分析模块

### **核心模块设计**

**1\. Benchmark Loader（测试任务加载）**

- 支持上传 CSV / JSON 格式的 Benchmark 文件。

- 读取任务 ID、场景、学科、Query 等字段。

- 将测试数据转换为系统可执行的标准化任务。

**2\. Model Adapter（模型统一调用）**

- 配置豆包 Doubao Seed 2\.1 Lite、DeepSeek V4\.1 Flash、智谱 GLM\-5\.3三个模型的 API。

- 统一封装不同模型的调用接口。

- 将相同 Query 分别发送给三个模型。

- 记录模型调用状态及响应结果。

**3\. Result Collector（结果采集）**

- 保存各模型的完整生成内容。

- 记录模型名称、对应 Query、响应时间及 Token 消耗。

- 记录 API 调用失败等异常信息。

- 将生成结果统一保存，供后续机评和人评使用。

**4\. LLM Judge（自动评测）**

- 调用qwen3\.8\-max作为独立 Judge 模型，对被测模型输出进行自动评分。

- 仅针对「需求满足度」和「输出完整性与规范性」两个机评维度进行评价。

- 根据当前 Benchmark Query 的具体任务要求，自主生成任务级评分检查项及 1—3 分判断依据，并进行完整性与合理性核对。

- 使用核对后的同一套评分标准，分别评价三个被测模型的输出。

- 输出维度得分、评分理由及问题记录，并保存评分标准和评测结果。

**5\.** **Human Evaluation Manager（人工评测管理）**

- 根据模型生成结果创建人工评测任务。

- 对模型名称进行匿名处理，并随机打乱结果顺序。

- 为评测人员生成共享评测链接。

- 接收并保存每位评测人员的五维度评分。

- 汇总多人评分，计算各维度人工评分结果。

**6\.Score Calculator（综合评分计算）**

- 获取 LLM Judge 的机评结果。

- 获取人工评测的汇总结果。

- 按照既定维度权重和机评、人评加权规则计算综合得分。

- 计算各模型的五维度得分及最终综合得分。

- 保存最终评分数据，供结果分析模块调用。

### **异常处理**

- 模型调用失败：记录失败原因，支持重新调用。

- Judge 评测失败：保留模型生成结果，支持重新机评。

- 数据保存失败：提示异常，不将未成功保存的数据标记为完成。
